A 10-bit calculator made of redstone

Twenty levers, eight buttons, four lamp digits and half a million blocks in between. Set the operands, press an operation, and watch the answer propagate — one game tick at a time, at the speed it would run in Minecraft.

Everything tagged measured was simulated on placed blocks. Everything tagged projected is an estimate and says so.

The machine, thinking

Flip bits into A and B, then press an operation. The button is held down for 40 game ticks and released, exactly as a stone button behaves, and the machine is then simulated tick by tick: white is the wavefront — every block whose state changed in the last few ticks — and it fades back to the block's own colour behind.

Be clear what 1× is asking for: that is Minecraft's own 20 ticks per second, and this machine takes 2,584 game ticks — a little over two minutes — to get from the keypress to the lamps. The wait is the real one. The default 10× makes it about thirteen seconds, and skip to settled jumps straight to the answer.

What is actually in there

Every stage is redstone; nothing is emulated. The pieces are separate modules in the source, each with its own tests, and they compile into one netlist and one placed world:

20 operand levers ──▶ A, B
 8-button keypad  ──▶ one-hot latches ──▶ 3-bit opcode
                  ──▶ 10-bit ALU  (8 operations, 4 flags)
                  ──▶ binary to BCD  (combinational double dabble)
                  ──▶ four seven-segment decoders  (leading zeros blanked)
                  ──▶ wiring loom  (32 nets, 128 risers, no crossings)
                  ──▶ four lamp digits + a flag row

They are one netlist rather than several placed side by side for a measured reason. The compiler gives each logic stage its own Y plane, and a stage's rail length is set by how many gates sit in that stage — so pipelining the ALU into the converter into the decoders uses disjoint stages and costs no extra rail, while splitting them into separately placed modules would add an inter-module loom for every signal crossing each boundary. The modules are in the source; the silicon is one block.

Three things worth pointing at

The keypad cannot burn out

Each key drives a repeater held from the side. Every button also feeds a shared any key is down bus, and each latch's lock is that bus inverted — so all eight go transparent together and the pressed key stores 1 while the rest store 0. One-hot, with no torch in the latch cell.

Leading zeros cost nothing

A digit is shown if it or anything above it is non-zero — one flat OR over every bit from there up. It folds into the decoder's minterms as one more literal, and a term is already an AND, so blanking is free.

The top digit needs no decoder

A 10-bit result cannot exceed 1023, so its thousands digit is 0 or 1 and its upper bits are the constant rail. The decoder folds: impossible values drop out of the sum and the segments lit for every reachable value become constants.

What it costs to keep stable measured

Minecraft kills a redstone torch forced off more than eight times in 60 game ticks, and hazard glitching in a network 36 stages deep does exactly that. Two independent things reduce it, and the second one is the interesting one.

Slower repeaters, over the same fourteen vectors:

Spacing is real and it is not sufficient — but it is the more interesting number, because a player cannot flip twenty levers inside a twentieth of a second. Changing every input in the same game tick aligns every hazard in the machine at one instant, which is a load the build never sees in a world with a person in it. The machine therefore moves only the levers that differ, two game ticks apart, and the page does the same when you click a bit.

The structural fix is the torch-free tap below: a comparator has no burnout rule at all, so the question would stop existing rather than being paid for in latency.

Where the size goes — and the one fix left measured

Mk I's lesson was that 85% of the latency was wire. Mk III exposes the same problem in a second dimension, and this time the cause is a specific line in the router.

A gate's collector runs along Z from its first tap to an exit, and that exit has to sit past the gate's own last tap — otherwise the collector would not reach it. The exit then becomes a rail for the next stage, whose gates tap it, whose exits must sit past those taps. Over 36 stages the Z coordinate ratchets upward and never comes back down:

The widest stage in the machine has 119 gates, which needs 476 blocks of Z. The machine is 1,825 blocks deep. Roughly three quarters of that depth is drift, not logic — and every block of drift lengthens the collectors that cross it, which is where the repeaters go.

The fix is specific: alternate the collector direction stage by stage, so exits are placed below the taps on odd stages and above on even ones. Z would then oscillate inside a band set by the widest stage instead of ratcheting with depth. projected That is the next thing to build, and it is measurable the same way this was.

Getting it into Minecraft

The build exports two ways, both vanilla — no mods for either:

Structure files

A grid of .nbt files a structure block loads, plus a manifest giving each one's offset. Structure blocks stop at 48 blocks a side, so a machine this size arrives as a jigsaw.

A datapack

/setblock and /fill commands, split into batches a server can run without stalling, placed relative to wherever you stand. Runs of identical blocks collapse into one /fill — most of this machine is the floor under the dust.

One convention is worth stating because getting it wrong fails silently — the build looks perfect and computes nothing. Minecraft's repeater facing runs from the output side to the input side, the opposite of this simulator's; comparators match repeaters; and a wall torch's facing points away from its support, the opposite of the simulator's attach. All three are flipped on the way out, and a test asserts each one.

A caution rather than a caveat: half a million redstone components in one world is far past what a Minecraft server ticks comfortably. This is a build that is honest about being a simulation artefact first.

What is left

  1. Alternating collector direction — the Z ratchet above. Biggest single win on size, and size is latency here.
  2. The torch-free inverting tap — a comparator in subtract mode inverts as fast as a torch and has no burnout rule, which would let the whole machine run at delay 1.
  3. Multiply and divide. The ALU has the eight operations a combinational unit can do in one pass; the other two need sequencing, which means a clock and a register file.
  4. A decimal keypad for the operands, which needs BCD-to-binary on the way in — the converter here runs the other way.
