A 10-bit calculator made of redstone

Twenty-eight levers on one wall, four lamp digits and half a million blocks in between. Set the operands, choose an operation, and watch the answer propagate — one game tick at a time, at the speed it would run in Minecraft.

Everything tagged measured was simulated on placed blocks. Everything tagged projected is an estimate and says so.

The machine, thinking

Flip bits into A and B, then choose an operation. Its lever is held down for 40 game ticks and released, and the machine is simulated tick by tick from there.

What you are watching is signal level, not on and off. Redstone dust carries a strength from 15 down to 0, losing one per block, and here that level is the wire's colour and its height — a line at 15 stands three times as tall as one at 1. A signal fading along a run is therefore a visible ramp, and a wavefront is a ridge that travels. Components that actually switch get their own hotter flash, held longer than the dust highlight, because those are the events and the dust between them is the consequence. Click any block to read its exact strength and state.

Be clear what 1× is asking for: that is Minecraft's own 20 ticks per second, and this machine takes 2,640 game ticks — a little over two minutes — to get from the keypress to the lamps. The wait is the real one. The default 10× makes it about thirteen seconds, and skip to settled jumps straight to the answer.

What is actually in there

Every stage is redstone; nothing is emulated. The pieces are separate modules in the source, each with its own tests, and they compile into one netlist and one placed world:

28 levers, 2 rows ──▶ A, B, and the operation   (one wall, one place to stand)
 8 of them latch one-hot ──▶ 3-bit opcode
                  ──▶ 10-bit ALU  (8 operations, 4 flags)
                  ──▶ binary to BCD  (combinational double dabble)
                  ──▶ four seven-segment decoders  (leading zeros blanked)
                  ──▶ wiring loom  (32 nets, 128 risers, no crossings)
                  ──▶ four lamp digits + a flag row

They are one netlist rather than several placed side by side for a measured reason. The compiler gives each logic stage its own Y plane, and a stage's rail length is set by how many gates sit in that stage — so pipelining the ALU into the converter into the decoders uses disjoint stages and costs no extra rail, while splitting them into separately placed modules would add an inter-module loom for every signal crossing each boundary. The modules are in the source; the silicon is one block.

Three things worth pointing at

The keypad cannot burn out

Each key drives a repeater held from the side. Every button also feeds a shared any key is down bus, and each latch's lock is that bus inverted — so all eight go transparent together and the pressed key stores 1 while the rest store 0. One-hot, with no torch in the latch cell.

Leading zeros cost nothing

A digit is shown if it or anything above it is non-zero — one flat OR over every bit from there up. It folds into the decoder's minterms as one more literal, and a term is already an AND, so blanking is free.

The top digit needs no decoder

A 10-bit result cannot exceed 1023, so its thousands digit is 0 or 1 and its upper bits are the constant rail. The decoder folds: impossible values drop out of the sum and the segments lit for every reachable value become constants.

What it costs to keep stable measured

Minecraft kills a redstone torch forced off more than eight times in 60 game ticks, and hazard glitching in a network 36 stages deep does exactly that. Two independent things reduce it, and the second one is the interesting one.

Slower repeaters, over sixteen vectors, re-measured on the build with the control wall — which matters, because that wall added 196 torches:

repeater delayresult
2 (4 gt) 2/16 correct, 146 torches burned out
3 (6 gt) 16/16 correct, but one torch burned out
4 (8 gt) 16/16 correct, none burned, 2,640 gt to the answer

The middle row moved. Before the control wall, delay 3 was clean over the same vectors and only failed on a hostile sequence; 196 more torches was enough to make an ordinary one cost a torch. Burnout margin is not a property of the logic — it scales with how much torch there is to glitch.

Inputs that arrive at human speed. On the earlier build, delay 3 only failed once it was handed a hostile sequence — operand pairs chosen to change ten or more levers at once. Varying only how far apart the flips were placed in time, over ten such vectors:

Spacing is real and it is not sufficient — but it is the more interesting number, because a player cannot flip twenty levers inside a twentieth of a second. Changing every input in the same game tick aligns every hazard in the machine at one instant, which is a load the build never sees in a world with a person in it. The machine therefore moves only the levers that differ, two game ticks apart, and the page does the same when you click a bit.

The structural fix is the torch-free tap below: a comparator has no burnout rule at all, so the question would stop existing rather than being paid for in latency.

Is the simulator right? measured

Everything above checks the machine against arithmetic. None of it checks the simulator against Minecraft — those tests all share one understanding of the rules, so a misunderstanding would be invisible to every one of them. Two separate checks now exist.

Each rule, alone. Thirteen rules, each with its own minimal circuit, so anyone who wants to confirm one against the game can build exactly that and look: dust decay over twenty blocks, strong versus weak power, dot/line/corner pointing, torch inversion timing, burnout at the ninth state change inside 60 ticks, all four repeater settings, repeater locking, both comparator modes, lamp powering, and the fact that a pulse shorter than a repeater's delay is swallowed entirely.

Each engine, against another engine. The rules are implemented a second time, deliberately badly — no precomputed nets, no dirty sets, every tick re-flooding every dust cell from every source. The two run side by side and every block is compared at every tick: 40 random circuits and a compiled gate array. That does not prove the rules match Minecraft, which is why each rule is also a circuit you can build. It proves the fast engine everything rests on behaves like the slow obvious one.

It found a real bug on the first run. What a repeater reads out of the cell behind it ignored which way that cell's repeater faced, so one pointing away would feed it anyway — fixed in both the Python engine and the JavaScript one this page runs. The machine happened not to depend on it, because rails always put dust or a solid block behind a repeater, but that was luck rather than design.

Using it in game measured

Correctness says nothing about whether a player can operate the thing. The compiler puts input rails on a four-block Z pitch, so twenty operand bits land spread over eighty blocks, and the keypad's buttons sit a dozen blocks above where those levers end up. Measured in Minecraft's own units — clicks, blocks walked, blocks climbed, and how many standing spots its ~4.5 block reach forces, taken from the player's eyes — that was miserable:

All 28 controls go on one wall: fourteen columns on a two-block pitch, two rows four apart, operation keys first so they sit beside the low-order bits, then bit i with A above B in a single column. The glass walkway in front of it is not decoration — with your feet level with the bottom row, the top row is a 2.6-block reach, which is why the table has no climbing in it.

The operation keys moved by substitution rather than rewiring. A key's button cell is a solid block that feeds the shared “any key is down” bus one way and its own delay chain the other; the keypad now simply leaves that cell empty and the panel's torch tower tops out exactly there. Both readers still see the signal in the same instant, so the release race the delay chain exists to win is untouched.

The routing is crossing-free by construction rather than by search — after the loom bug below, that was a deliberate choice. Each net takes four legs and every leg sits on a coordinate nothing else shares: out along its row's own height at its own panel Z, up a tower at its own turn column, along Z at that column, then in at one shared height on the target's own Z, unique because two controls cannot drive the same cell.

It did not stop me building it wrong twice, and both failures were silent: lint passed, every lever existed where the machine said it did, and the answer was quietly zero. First the run doubled back over its own lever and buried it in dust — World.set overwrites without complaint. Then, with the keys on the panel, a net's Z-run could be a single cell, and line() inferred a run's direction from its endpoints, which for one cell say nothing: it guessed south, that net needed north, and one repeater in the middle of a live route sat facing the tower it was supposed to feed. Both are assertions now — a test watches every write on the full machine and insists all 28 controls are still levers, and a one-cell run has to say which way it flows.

The row that matters is the fifth: editing a couple of bits is what using a calculator consists of, and that went from 93 blocks of walking to eleven. What the panel does not fix, and the same tool reports it, is that the digits are 657 blocks away and 192 up — the controls are at the input end of a machine 865 blocks long. That needs a second display fed by a 32-net relay running the length of it, and it is written down rather than half-built.

A third silent failure, this time in the interface measured

Reported from a phone: A = 10, B = 72, ADD highlighted, answer 20. Twenty is not a wrong sum — it is 10 << 1, exactly right for SHL. The redstone was doing precisely what it had been asked; the page had asked wrongly.

This page holds an operation lever down for 40 game ticks and then releases it, and it tracked one pending release. Press a second operation inside that window and the first record was overwritten, so that lever was never let go. Two keys held down is not a fault in the keypad — it has a perfectly good answer, both latches store 1 and the opcode becomes their OR — and SHL(110) | ADD(000) is SHL. The machine then computed SHL under ADD's highlight, and reported itself stable, because it was.

Two fixes, and the second is the one that matters. The page now releases every key still held before pressing a new one, the way a hand leaves one lever before reaching for the next. And the highlight is no longer a memory of what was clicked: it is read back from the keypad's one-hot rails, the same way the digits are read off the lamps. If two latches are ever lit, the page says so and names the OR. A page that reports the machine cannot disagree with it.

Where the size goes — and the one fix left measured

Mk I's lesson was that 85% of the latency was wire. Mk III exposes the same problem in a second dimension, and this time the cause is a specific line in the router.

A gate's collector runs along Z from its first tap to an exit, and that exit has to sit past the gate's own last tap — otherwise the collector would not reach it. The exit then becomes a rail for the next stage, whose gates tap it, whose exits must sit past those taps. Over 36 stages the Z coordinate ratchets upward and never comes back down:

The widest stage in the machine has 119 gates, which needs 476 blocks of Z. The machine is 1,825 blocks deep. Roughly three quarters of that depth is drift, not logic — and every block of drift lengthens the collectors that cross it, which is where the repeaters go.

The fix is specific: alternate the collector direction stage by stage, so exits are placed below the taps on odd stages and above on even ones. Z would then oscillate inside a band set by the widest stage instead of ratcheting with depth. projected That is the next thing to build, and it is measurable the same way this was.

Getting it into Minecraft

The build exports two ways, both vanilla — no mods for either:

Structure files

A grid of .nbt files a structure block loads, plus a manifest giving each one's offset. Structure blocks stop at 48 blocks a side, so a machine this size arrives as a jigsaw.

A datapack

/setblock and /fill commands, split into batches a server can run without stalling, placed relative to wherever you stand. Runs of identical blocks collapse into one /fill — most of this machine is the floor under the dust.

One convention is worth stating because getting it wrong fails silently — the build looks perfect and computes nothing. Minecraft's repeater facing runs from the output side to the input side, the opposite of this simulator's; comparators match repeaters; and a wall torch's facing points away from its support, the opposite of the simulator's attach. All three are flipped on the way out, and a test asserts each one.

A caution rather than a caveat: half a million redstone components in one world is far past what a Minecraft server ticks comfortably. This is a build that is honest about being a simulation artefact first.

What is left

  1. Alternating collector direction — the Z ratchet above. Biggest single win on size, and size is latency here.
  2. The torch-free inverting tap — a comparator in subtract mode inverts as fast as a torch and has no burnout rule, which would let the whole machine run at delay 1.
  3. Multiply and divide. The ALU has the eight operations a combinational unit can do in one pass; the other two need sequencing, which means a clock and a register file.
  4. Decimal entry, which is the last big thing standing between this and something a person would call usable: eight ten-key pads, one per digit position, and BCD-to-binary on the way in — the converter here runs the other way. The control wall already carries every input on a two-block pitch, so the panel would take them unchanged; the logic would not.
  5. A second display beside the controls. The wall fixed entry and did nothing for reading: the digits are 657 blocks away and 192 up. That needs a 32-net relay the length of the build and a descending run, which this router cannot yet place.
